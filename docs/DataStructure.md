## Task

The only structure in the project. It is a JPA entity mapped to the `task` table and exposed as JSON under the same name.

| Field   | Type    | Description                                            |
|---------|---------|--------------------------------------------------------|
| `id`    | integer | Primary key, database-generated on insert, never sent by the client |
| `title` | string  | User-provided label                                    |
| `done`  | boolean | Completion status, toggled via checkbox (PUT)          |

`id` is generated by the database on insert and returned to the client. A task with a missing `id` in the request body is valid (the field is simply ignored).

`done` is never read on creation: the service builds a fresh task from the submitted `title` alone, so a client sending `done: true` gets a task stored as not done. Updating an existing task does write both fields.

The entity exposes a no-arg constructor and accessors, and carries no relation to another entity.

## Storage

| Profile | Storage                                          |
|---------|--------------------------------------------------|
| dev     | H2 file database, `backend/data/taskbase.mv.db`, git-ignored |
| prod    | PostgreSQL, database and role from the environment |
| test    | H2 in-memory database, discarded after the run   |

Tasks survive a backend restart in dev and prod. The dev database is deleted with `backend/data/`, so removing that directory is a full reset.

The schema is created by Hibernate on startup rather than by migrations: missing tables and columns are added, changed ones are not migrated. See `Optimisations.md`.
